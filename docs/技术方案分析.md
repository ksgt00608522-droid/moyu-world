## 二、已验证结论（本机实测）

测试环境：Windows + Edge（Chromium 内核），通过 CDP 直连页面求值，非推测。

### 2.1 `file://` 协议下的能力

| 能力 | 结果 | 对设计的约束 |
|---|---|---|
| 普通 `<script src="js/x.js">` | 可用 | 多文件开发可行，不强制打包 |
| ES Module（import / export） | 被拦截 | **禁止使用模块化语法** |
| `fetch('./data.json')` | TypeError | **数据不能是 .json，要写成 .js** |
| localStorage / sessionStorage | 可用 | 可做顺手存档 |
| IndexedDB（建库 + 事务写） | 可用 | 可选，本项目体积下非必需 |
| `showSaveFilePicker` | 可用 | 通过安全上下文检查，仅要求真实点击 |
| Blob + `<a download>` | 可用 | 导出存档可行 |
| `isSecureContext` | `true` | `file://` 属于安全上下文 |

### 2.2 中文编码

| 场景 | 结果 |
|---|---|
| UTF-8 无 BOM，HTML 无 charset 声明 | 中文正确显示（浏览器检测器命中） |
| UTF-8 无 BOM，HTML 有 `<meta charset="utf-8">` | 中文正确显示 |
| 外部 `zh.js` 中的中文字符串 | 两种情况均正确解码 |

当前浏览器能正确处理，但**这是编码检测器的运气，不是保证**。真正的隐患是中文 Windows 上部分编辑器默认存成 GBK——那种文件在本机看着正常，发给别人就乱码。

硬性约定：所有文件一律 **UTF-8 无 BOM**，HTML 显式声明 charset，构建脚本加一道编码检查。详见 `docs/设定/08-技术约束.md`。

## 三、风险清单

| # | 风险 | 严重度 | 状态 | 对策 |
|---|---|---|---|---|
| 1 | 中文乱码（文件被存成 GBK） | 高 | 已实测，需约定 | 全 UTF-8 无 BOM + 构建时编码检查 |
| 2 | ES Module 在 file:// 下失效 | 高 | 已确认 | 普通 script + 全局命名空间 |

| 13 | 单文件体积膨胀 | 低 | 估算约 150 KB | 无风险，无需优化 |

## 四、受平台约束的技术决定

以下几条不是设计选择，而是被"双击即玩"这个交付方式强制的，没有商量余地：

1. 不使用 ES Module，全部走普通 `<script src>` + 全局命名空间。
2. 数据文件不用 `.json`，写成 `G.data.x = [...]` 形式的 `.js`。
3. 开发期就用 `file://` 双击调试，不引入本地服务器。
4. 所有文件 UTF-8 无 BOM，HTML 显式声明 charset。

完整的技术约束与代码组织方式见 `docs/设定/08-技术约束.md`。

## 六、明确不做

- 后端 / 账号 / 云同步
- npm 依赖树（`node_modules` 保持不存在）
- Canvas / WebGL / 游戏引擎
- Service Worker / PWA 离线缓存（file:// 下也注册不了）
- 打包器、转译器、类型系统
- 移动端适配（iOS 打开本地 html 基本不可行）
