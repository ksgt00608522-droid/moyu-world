# 09 NPC 与任务

> 状态：骨架已定（玩法待定）
> 负责：NPC 的数据结构、地图上的呈现、态度分、任务的定义与进度、对话
> 不负责：NPC 说什么话（见 01）、掉落与奖励（见 06）、战斗数值（见 04）、
>         事件点本身（见 `10-事件点.md` —— 这里只讲它作为任务目标的那一面）

---

## 为什么单独一份

NPC、任务、对话是**三件事**，但互相咬得紧（任务挂在 NPC 身上、对话把两者连起来），
拆成三份会来回翻，所以合一份，但内部严格分节：

- **NPC 是什么**（长什么样、站哪里、什么颜色）→ 第一节
- **任务是什么**（要做什么、做到哪了）→ 第二节
- **对话**（怎么把任务接到手上）→ 第三节

数据也是分开存放的，各管各的：NPC 在 `data/npcs.js`，任务在 `data/quests.js`，
对话状态在 `js/talk.js`。

## 一、NPC

### 三张表（都在 `data/npcs.js`）

一个文件里放三块数据，顺序无所谓，但都必须写在 `G.data` 建好之后
（即 `js/data.js` 要先加载）。

#### 1. 类型表 `G.data.npcTypes`

NPC 按类型上色。**加类型只改这里**，不用碰 CSS 也不用碰 JS ——
地图渲染时会把 `color` 写成那一格上的 CSS 变量 `--npc-color`，怎么用这个颜色留在 CSS 里。

| 字段 | 含义 |
|---|---|
| `id` | 类型标识 |
| `name` | 显示名，出现在「地图点位状态」面板里 |
| `color` | 地图上那个字的颜色，**同时也是那一格边框的颜色** |

类型有多少种**还没定**，先只放了 `common` / `mystery` / `merchant` 三种，随时可以加。

#### 2. 态度阶段表 `G.data.attitudeStages`

态度是 **0–100 的分数**，按门槛切成几个阶段。

| 字段 | 含义 |
|---|---|
| `min` | 这个阶段从多少分开始（**含**） |
| `name` | 阶段名 |
| `color` | 面板里显示这个阶段名用的颜色 |

**硬性约定：**

- **数组必须按 `min` 升序排列。** 映射函数是「从头扫到尾，取最后一个满足 `分数 >= min` 的」，
  顺序错了会取到错误的阶段。`validate.mjs` 强制检查升序。
- **第一项的 `min` 必须是 0。** 否则分数落在 0 和第一档之间时会取到兜底值，显示成空阶段。
- 分数会被**夹在 0–100**（见 `js/rules.js` 的 `attitudeStage()`），传负数或超过 100 都不会崩。

**现阶段态度只是展示，没接任何玩法**（不改变 NPC 行为、不影响任何判定）。

#### 3. NPC 表 `G.data.npcs`

| 字段 | 含义 |
|---|---|
| `id` | 唯一标识，`npc_` 前缀 + 小写字母数字下划线 |
| `name` | 名字，显示给玩家 |
| `glyph` | **地图上画的那个字。** 跟 `name` 分开定义 —— 名字往往两三个字，格子只放得下一个 |
| `type` | 类型 id，决定地图上的颜色，必须在 `npcTypes` 里 |
| `attitude` | 态度分，0–100 的整数 |
| `talk` | **普通对话台词**，非空字符串数组，见下 |
| `at` | **出现位置**，一个数组，见下 |

**NPC 身上没有任务字段。** 任务挂在谁身上由任务自己声明（`giver`），
见本节后面的「任务与 NPC 不是绑定关系」。

### `talk`：一组自己的台词

```js
"talk": [
  "……你身上有股新来的味道。",
  "这地方以前不是这样的。灯一直亮着，可没人记得是谁点的。"
]
```

- **每个 NPC 一组自己的台词**，跟别人不共用。
- 每次开口**随机挑一句**。走 `G.rng`（统一种子源），不是 `Math.random()` ——
  读档后不会因为反复对话刷出不一样的结果。
- **任务对话不写在这里**，那是任务自己的 `offer` / `turnin`。
  这里只放"没事闲聊"的话。
- 数组为空时会退化成一句通用兜底（`talk.silent`），不报错。

### `at`：一个 NPC 可以出现在多个地方

```js
"at": [
  { "room": "room_hall",  "x": 4, "y": 2 },
  { "room": "room_right", "x": 2, "y": 3 }
]
```

- 一个 NPC 可以出现在**多个房间、多个区域**，也可以在**同一个房间里出现好几处** —— 就写多条。
- 每一项的 `room` 必须在 `data/rooms/*.js` 里存在，坐标必须在图内、不能是墙。
- **不能开在门格上。** 门是通道，站个人会把路堵住。
- **不能开在出生点上。** 否则玩家一睁眼就站在别人身上。

「同一个人出现在多处」在实现上是同一个 `id`、同一份态度、同一份任务进度 ——
不是复制成好几个 NPC。所以 `npcsIn(room)` 会去重：进房间时的「这里有人：xxx」只报一次名字。

### NPC 挡路

**玩家走不到 NPC 那一格上。** `G.data.walkable()` 把 NPC 算成障碍物
（`walkable(room, x, y, npcIdx)` 的第 4 个参数是可选索引，渲染地图时透传，
免得每个格子都重建一遍）。

配套的三条：

1. **撞上人时说的话跟撞墙分开。** 撞墙说「那边是墙，过不去」，撞人说
   「神秘人挡在前面，过不去」—— 都说"墙"会让玩家以为地图画错了。
2. **能对话的只可能是四邻。** 人只可能在旁边，不可能在脚下，所以
   `G.data.npcsNear(room, x, y)` 报的是上下左右四邻站着的人。
3. **NPC 不能把路堵死。** `validate.mjs` 从出生点按"NPC 挡路"的规则做一遍
   BFS，每个门格都必须走得到。

### 地图上怎么画

| 情况 | 画什么 | 类名 |
|---|---|---|
| 站在这一格 | `glyph`，颜色取自类型的 `color` | `npc`，有活可干时加 `has-quest` |

- **画的是 `glyph`，不是 `name`。** 这是这个字段存在的全部理由。
- 满宽汉字照 `--fs` 那么大会贴着格子边，所以 NPC 那一格的字**单独缩到 0.7**
  （跟门格一样的处理）。
- **边框用类型色。** 跟玩家格的绿框同一个做法：`inset` 阴影画的，**不占布局**，
  格子宽高不会被挤动。颜色走同一个 `--npc-color` 变量，改类型表就换色。
- 角标用 `::after` 画，**不额外塞一个元素** —— 那会破坏「一行 flex、格子定宽定高」的排版前提。
  角标在右上角，大小是格子的 0.24，最小 4px。

### 角标亮不亮

`G.quests.npcBusy(npc, room)`：这个人身上**还有没有"现在就能做的动作"** ——
有可接的、或者有能交的，就亮。

**问的是"还有没有活要干"，不是"有没有任务"。** 所以：

- 任务还在进行中（没达成）时**不亮** —— 此刻找他也做不了什么。
- 任务做完了、也交完了、也没有下一个可接 → **不亮**。

> ⚠️ **可重复任务会让角标常亮。** 交付后它立刻回到"可接"，所以那个 NPC
> 永远有活给你，角标就一直挂着。语义上没错，但确实会一直占着一个角标。
> 要不要改成只标"可交"的，见 `99-待定问题.md` 的 H 组。

### 一级区里怎么显示

**站在人旁边（四邻）时**，中栏「地图点位状态」多出一块：

```
旁边的人
神秘人                     ← 用类型的颜色
神秘 · 中立 50             ← 类型名 · 态度阶段名 分数
[  跟神秘人说话  ]          ← 按钮
```

- 名字叫「旁边的人」而不是「脚下的人」—— NPC 挡路之后人只可能在旁边。
- 人名用类型色，态度阶段名用阶段色，颜色全部来自数据表，`ui.js` 只负责搬运。
- **一人一块，旁边有几个人就画几块。**
- **说话时这一块照样在。** 正在说话的那个按钮换成高亮（`button.cur`），
  其余的不动 —— 这样点另一个人的按钮就**直接切过去**，不用先按「结束对话」。
  这是「一级 / 二级」这个拆法真正要解决的问题，详见 `02-玩法循环与操作.md`。
- **不列任务进度。** 谁身上有活，地图那一格右上角的角标已经在说了；
  做到哪一步属于"点开才关心"的事，在二级操作里看。

### 二级操作里怎么显示

**开口之后**，右栏「二级操作」里是：

```
正在跟神秘人说话            ← 抬头，人名用类型色
「……你身上有股新来的味道。」 ← 他刚说的那一句
走十步 3 / 10               ← 进行中的任务报进度
[  随便聊聊        ]
[  接受：走十步     ]
[  结束对话        ]
```

- 任务那一行三档颜色：进行中 = 暗（只是信息）；**可以交差了 = 金色**（提醒去做正事）；
  已完成 = 更暗（退到背景里）。**没有任务就不画这一行**，不是画一行空的。
- 进度那一行的数字**对 `collect` 是现算的**（"三株清心草 1 / 3"里的 1 是
  `G.items.count('itm_herb')`），不是 `progress` 字段 —— 见上面「`collect`：收集类目标」。
- 能接 / 能交的任务**不在这里列成信息行** —— 它们会变成选项按钮，不重复说一遍。
- **名字和态度不在这里重复画。** 一级区那两行就是给这个用的，而且当前说话的那个人
  在一级区是高亮的 —— 两块面板各讲自己那一层。
- 没在说话时这里是一句灰提示（文案 `ui.secondaryIdle`），不是一片空白。

### 进房间时提一句

`world.describe()` 在房间描述之后多一句「这里有人：神秘人、商人。」。
**不说在哪个位置** —— 那属于"看一眼地图"的事，写进日志反而要玩家自己对照坐标。

## 二、任务

### 定义在 `data/quests.js`

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | ✔ | 唯一标识，`q_` 前缀 + 小写字母数字下划线 |
| `name` | ✔ | 任务名，显示给玩家 |
| `desc` | ✔ | 描述 |
| `goal` | ✔ | 目标，`{ type, count }` |
| `giver` | ✔ | **发布这个任务的 NPC id。** 任务挂在谁身上看这个 |
| `room` | | 只在哪个房间出现。NPC 出现在多个房间时用它限定 |
| `requires` | | 前置任务 id。**前置没交付，这个任务完全不出现** |
| `repeatable` | | 默认 `false`。`true` = 交付后可以反复再接 |
| `reward` | | 交付时给什么（钱 / 物品），见下面「任务奖励」 |
| `offer` | | 接取时 NPC 说的话。不填用通用文案 |
| `turnin` | | 交付时 NPC 说的话。不填用通用文案 |

`goal.type` 现在支持四种：

| 类型 | 写法 | 谁推进 |
|---|---|---|
| `walk` | `{ "type": "walk", "count": 10 }` | `G.quests.add('walk', 1)` |
| `reach` | `{ "type": "reach", "count": 1, "ev": "ev_spring" }` | `G.quests.reach(evId)` |
| `use` | `{ "type": "use", "count": 1, "ev": "ev_spring" }` | `G.quests.use(evId)` |
| `collect` | `{ "type": "collect", "count": 3, "item": "itm_herb" }` | **不用推进**，现算，见下 |

`reach` / `use` 是**指定事件点**的目标（走到某处 / 跟某处互动），
**必须写 `ev`** —— 完整规则见 `10-事件点.md` 第九节。
`collect` 必须写 `item`，见下面「`collect`：收集类目标」。

以后加击杀就是 `kill` —— **加类型要同时改三处**：
`tools/validate.mjs` 里的 `GOAL_TYPES`、`data/quests.js` 的说明，
以及谁去调推进入口（现在是 `js/world.js`）。

### `collect`：收集类目标

```js
"goal": { "type": "collect", "count": 3, "item": "itm_herb" }
```

**它跟另外三种不是一回事。** `walk` / `reach` / `use` 是"累计推进"，`collect` 是**现算**：

| | 另外三种 | `collect` |
|---|---|---|
| 怎么算进度 | 存档里的 `progress` 累加 | **现算** `G.items.count(item)` |
| 谁推进 | `add()` / `reach()` / `use()` | **没人推进** —— 捡到就自动算数 |
| `progress` 字段 | 用 | **不用**（写了也没人看） |
| 达成条件 | `progress >= count` | 当前持有量 `>= count` |

**为什么不能累计推进**：那样"捡到 3 株草 → 用掉 1 株"进度还停在 3 / 3，
玩家会以为可以交差，交付时却发现草不够。**现算就没有这个不一致**。

**交付时扣掉。** 交付 `collect` 任务时按 `goal.count` 从背包里扣 ——
不然同一批草能交无限次任务。扣完如果不够（比如交之前用掉了一株），
**不给交付**，提示一句差多少。

> 扣在"发奖励"**之前**，不然玩家能靠"先拿奖励再退货"刷东西。
>
> 扣了东西不退还：**交付是原子的** —— 要么"扣草 + 发奖励 + 改状态"全做完，
> 要么什么都没发生。中途失败不会出现"草没了但任务没交"的状态。

### 任务奖励

```js
"reward": {
  "money": { "coin": 30 },
  "items": { "itm_herb": 1 }
}
```

| 字段 | 含义 |
|---|---|
| `money` | 币种 id → **正整数** |
| `items` | 物品 id → **正整数** |

- **两个都可选，也都可以同时写。** 一个 `reward` 都没有的任务就是纯跑腿。
- **值是正整数，不带符号。** 奖励只有"给"，没有"扣" ——
  要扣钱那是任务的**代价**，是另一个字段，现在不做。
- 字段名是 `money` / `items`，**跟事件效果的键（`money` / `give`）故意不一样**：
  奖励是一份"清单"，不是一串按顺序执行的效果，两套东西不共用一个名字。
- **奖励没有 `log` 字段。** 交付时系统自动生成一行
  「拿到了：金币 ×30、清心草 ×1。」（文案 `quest.reward`），
  素材不用管 —— 也就不会出现"素材忘了写 log，玩家不知道拿到了什么"。

**发放时机**：交付成功之后、`state` 改掉之前。

### `requires` 看的是"交过差"，不是"到了终态"

前置任务的判定是 **`times > 0`（交付过至少一次）**，**不是 `state === 'done'`**。

对不可重复的任务两者等价（交过就是 `done`）。但**可重复任务交付后 `state` 立刻回到
`available`**，永远到不了 `done` —— 按 `state === 'done'` 判的话，
`requires` 指向一个可重复任务就会**永远不满足**，后面那个任务一辈子挂不出来。

> 现在有这种素材：商人那个可重复的「搭把手」（`q_patrol`）就是
> 「三株清心草」（`q_herb`）的前置 —— 交过一次「搭把手」才接得到。

### 演示素材

第 22 轮（背包系统）加了两个任务，把 `reward` 和 `collect` 各跑通一遍：

| id | 名字 | 发布 | 目标 | 奖励 | 演示的是 |
|---|---|---|---|---|---|
| `q_patrol` | 搭把手 | 商人 | `walk` 5（可重复） | `items: { itm_herb: 1 }` | `reward.items` |
| `q_herb` | 三株清心草 | 商人 | `collect` 3 × `itm_herb` | `money: { coin: 30 }` | `collect` 目标 + `reward.money` |

`itm_herb`「清心草」由事件点 `ev_herb`（大厅 7,5，可重复）给，
正好凑成一条闭环：**采草 → 攒够三株 → 交任务 → 拿钱**。

> 「搭把手」给的是清心草、「三株清心草」给的是钱 —— 故意错开的：
> 两条路各自演示一个 `reward` 字段，不用为了测试再去改素材。

### 任务与 NPC 不是绑定关系

**NPC 身上没有任务字段。** 是**任务自己**声明 `giver`（挂在谁身上）
和 `room`（只在哪个房间挂出来），由 `G.quests.ofNpc(npc, room)` 现算。

好处：同一个任务换个人发布，只改 `data/quests.js` 一行，不用动 NPC 素材；
同一个人在两个房间拿出不同的任务，也只靠 `room` 一行区分（商人就是这样：
「搭把手」写了 `room: room_right`，所以他站在大厅里时不拿出这个任务）。

`ofNpc()` 的过滤顺序：

1. `giver` 不等于这个 NPC → 跳过
2. 任务写了 `room` 而当前房间不是它 → 跳过
3. **前置没交付 → 跳过**（不是"显示了但灰着"，是根本不在返回里）

### 进度在 `js/quests.js`（`G.quests`）

**进度不缓存在模块里**，每次现读现写 `G.state.data.quests` ——
状态只有一份，不存在"内存和存档对不上"的问题。

`G.state.data.quests` 的形状是 `任务 id -> { state, progress, times }`：

| 字段 | 含义 |
|---|---|
| `state` | `'available'` / `'active'` / `'done'` |
| `progress` | 已推进的步数 |
| `times` | 交付过几次（可重复任务用它记完成次数） |

#### 三个状态

| 状态 | 含义 |
|---|---|
| `available` | **可接**（还没接） |
| `active` | 已接，进行中 |
| `done` | 已交付（不可重复任务的终态） |

**「没有记录」= `available`。** 这条约定有两个好处：

1. 旧存档（连 `quests` 字段都没有的）读进来，所有任务直接就是"可接"，不用迁移数据。
2. 任务临时下线再加回来时，进度还在（`normalize()` 故意不清理指向已删任务的记录）。

**「目标达成、等玩家去交差」不单独占一个状态** —— 它是 `active` 的派生结果：
`progress` 到了 `goal.count` 就是待交付（`isReady()`）。少一个状态少一处不同步。

### 未接收不可执行

**没接的任务不推进进度。** `G.quests.add(type, n)` 只认 `active` 的任务 ——
这就是"任务必须先被接收才能进行"。

`add()` **返回这一次刚刚达成目标的任务数组**，调用方拿去打日志
（`world.move()` 拿它说一句「任务目标达成：走十步。去找发布的人交差。」）。
注意返回的是"达成"不是"完成" —— 还要去找人交差才算完。

- 进度**夹在目标值上**，不会停在 `12 / 10` 那种看着像出错的状态。
- 只在**刚好跨过门槛**那一次报一次，不然每走一步都会说一遍。

### 谁推进进度

`G.world.move()` 每成功走一步调一次 `G.quests.add('walk', 1)`。
以后战斗加进来，击杀走同一个入口（`add('kill', 1)`），不用改这个模块。

### 任务链

任务链就是靠 `requires` 串起来的：

```
q_walk10 ──交付──> q_walk20 ──交付──> q_walk30
```

**前置没交付时，后一个任务完全不出现** —— 不在 `ofNpc()` 里，
所以 NPC 的对话选项里也看不到它。不是"显示了但灰着"。

`validate.mjs` 会检查 `requires` 指向真实任务、不能自指、**不能串成环**。

### 可重复任务

`repeatable: true` 的任务，交付后：

- `state` 立刻回到 `available`（马上又能接）
- `progress` 清零（下一次从零开始）
- `times` 累加（完成次数留在存档里）
- 记事里补一句「还能再接一次（已经做完 N 次）」，免得玩家以为出 bug 了

不可重复的任务交付后进 `done`，从此不再出现。

### 交付次数

`G.quests.times(id)`：交付过几次。不可重复任务交过一次就是 1。

## 三、对话

### 为什么单独一个模块（`js/talk.js`）

对话是一份**当前状态**，不是某一帧算出来的东西：

- 台词要随机挑一句，但**不能每次刷新面板都重挑**（`renderTile` 一刷新就跑一遍，
  台词会疯闪）。所以挑中的那一句必须存下来。
- "正在跟谁说话"也要记住，否则面板不知道该画谁。

这份状态**不进存档**：它是瞬时的，关掉游戏再打开不该还在跟人说话。

**不碰 DOM。** `ui.js` 要读对话状态来画面板（`ui → talk`），
所以 `talk` 不能反向调 `ui` —— 否则两个模块成环，违反"依赖方向严格单向"。
按项目的做法：`talk` 只**产出事件列表** `{ text, cls }`，
调用方（`main.js` 的 `runTalk`）负责拿去写记事和刷新。

### 对话是一串选项

**一个任务就是一个选项。** 同一个 NPC 身上可以同时挂着普通对话、可接的任务、
能交的任务 —— 它们并列成一排按钮，各点各的。

这些选项画在**右栏的二级操作**里，不在一级区。两块面板并排看是这样：

````
（一级区 · 中栏「地图点位状态」）   （二级操作 · 右栏）
旁边的人                          正在跟神秘人说话
神秘人                            「……你身上有股新来的味道。」
神秘 · 中立 50                    [  随便聊聊        ]   ← 普通对话
[  跟神秘人说话  ]  ← 高亮         [  接受：走十步     ]   ← 可接的任务（金色）
商人                              [  交付：再走二十步  ]   ← 已达成的任务（金色）
商人 · 友好 60                     [  结束对话        ]   ← 中性色
[  跟商人说话    ]
````

一级区列着旁边**所有**人，正在说话的那个只是高亮 —— 所以点「跟商人说话」
就当场切过去，不用先按「结束对话」。

`G.talk.options()` 返回这次能选什么：

| kind | 什么时候出现 |
|---|---|
| `chat` | 永远有 |
| `accept` | 任务 `available` 时 |
| `deliver` | 任务 `isReady()` 时（已接 + 目标达成） |

**进行中但没达成的任务不给选项**（此刻没什么可做的），它只在二级操作里
作为一行进度信息显示。

### 走开就自动结束

走一步就调一次 `G.talk.drop()`（见 `js/world.js` 的 `move`）。
另外 `current()` 也会**现算**"那个人还在我旁边吗" —— 双保险，
就算哪条路忘了 `drop`，面板也不会画出一个已经走远的人。

`current()` 返回 null 时，二级操作就回到空闲提示；一级区那边照旧列人
（旁边还有别人的话，按钮一个不少）。

### 指令

`talk` 后面可以带子命令，点位状态面板里的按钮就是把子命令写进 `data-arg` 传回来的：

| 指令 | 作用 |
|---|---|
| `talk` | 跟旁边的人说话（旁边只有一个人才行，多人会提示点哪一行） |
| `talk <npcId>` | 跟指定的那个人说话 |
| `talk chat` | 换一句普通台词 |
| `talk accept <questId>` | 接受任务 |
| `talk deliver <questId>` | 交付任务 |
| `talk bye` | 结束对话 |

`talk` 跟 `enter` 一样**不出现在操作区里** —— 它绑在人身上。
没站在人旁边时，那个按钮根本不存在。

## 四、素材完整性（强制）

下面这些由 `tools/validate.mjs` 强制检查，**写错直接报错**，不会等到运行到一半才炸。

**类型表：** `id` / `name` / `color` 必填，`id` 不能重复。

**态度阶段表：** `min` 必须是 0–100 的整数、**第一项必须是 0**、**必须严格升序**，
`name` / `color` 必填。

**任务表：**

- `id` 带 `q_` 前缀、`name` / `desc` / `goal` 必填
- `goal.type` 必须在支持列表里（`walk` / `reach` / `use` / `collect`）、
  `goal.count` 是正整数
- **`goal.type === 'collect'` 时必须写 `goal.item`**，且指向真实存在的物品
  （`data/items.js`）—— 跟 `reach` / `use` 必须写 `ev` 一个道理
- **`goal.item` 只能出现在 `collect` 上**，写在别的类型上直接报错
  （写了也不会被读，等于一句自欺欺人的备注）
- **`giver` 必填**，且必须能在 NPC 表里找到
- `room` / `requires` / `offer` / `turnin` 若填了，必须是非空字符串
- `requires` 必须指向真实任务、**不能自指、不能串成环**
- `repeatable` 若填了必须是布尔
- **`reward` 若填了必须是对象**，只允许 `money` / `items` 两个键：
  - `reward.money` 的键必须指向真实存在的币种（`G.data.moneyTypes`），
    值是**正整数**
  - `reward.items` 的键必须指向真实存在的物品（`data/items.js`），
    值是**正整数**；**唯一物品（`stack: false`）不许大于 1**
  - **空 `reward`（`{}`）直接报错** —— 一个什么都不给的奖励不如不写

**交叉检查（任务 ↔ 素材）：**

- 每个任务的 `giver` 存在、`room` 存在
- **发布任务的 NPC 必须真的会出现在那个房间里** —— 否则这个任务永远挂不出来
- `requires` 指向的任务存在

**NPC 表：**

- `id` 带 `npc_` 前缀、`name` 必填
- **`glyph` 必须正好是一个字**（`Array.from` 算长度，表情符号也算一个）
- `type` 必须能在类型表里找到
- `attitude` 必须是 0–100 的整数
- **`talk` 必须是非空字符串数组**，每一项非空
- **`quest` 字段会直接报错** —— 已经废弃，任务改由 `data/quests.js` 的 `giver` 声明
- **`at` 必须是非空数组**；每一项的房间必须存在、坐标在界内、**不在墙里**、
  **不在门格上**、**不在出生点上**
- **同一个房间里同一格不能站两个 NPC**

**NPC 不能把路堵死：**

从出生点出发，按"NPC 挡路"的规则做一遍 BFS，**每个门格都必须走得到**。
新增 NPC 时如果正好卡在唯一的通道上，这一步会直接报错。

## 已废弃

### NPC 身上挂 `quest` 字段

废弃于加入任务链与可重复任务那次调整。

原因有两个：一是**一个 NPC 只能挂一个任务**，任务链（完成 1 才能接 2）根本表达不了；
二是**任务与 NPC 绑死了**，想让同一个人在不同房间拿出不同任务、
或者换个 NPC 发布同一个任务，都得改 NPC 素材。

改成：任务自己声明 `giver` / `room` / `requires` / `repeatable`，
由 `G.quests.ofNpc()` 现算。`validate.mjs` 现在见到 `quest` 字段直接报错。

### 所有任务一开始就是进行中（没有"接任务"这一步）

废弃于加入对话系统那次调整。

原因：任务不等玩家同意就自己开始跑，玩家既不知道自己接了什么，
也没法拒绝；而且 NPC 的对话就没有存在的意义了。

改成三态（可接 / 已接 / 已交付）+ 接取制：**没接的任务不推进进度**，
接和交都要通过跟 NPC 对话。

### NPC 不挡路

废弃于同一次调整。

原因：玩家能站到 NPC 那一格上，地图上就得画玩家自己的字把 NPC 盖掉，
点位状态也得用「脚下的人」这种别扭的说法；两个人重叠在一格，
以后加战斗、加碰撞都绕不开。

改成 NPC 算障碍物（`walkable()` 拦下），玩家只能走到旁边再跟它说话，
面板那一块也跟着改叫「旁边的人」。

### `G.quests.npcDone(npc)`

废弃于同一次调整。原来靠"NPC 的 `quest` 字段有没有做完"决定角标，
现在改成 `G.quests.npcBusy(npc, room)` —— 问的是"这人现在还有没有活给你"，
由任务自己的 `giver` / `room` / `state` 现算。

### 对话面板画在「地图点位状态」里、说话时把「旁边的人」顶掉

废弃于加入二级操作那次调整（完整说明见 `02-玩法循环与操作.md`）。

原因：一开口整块「旁边的人」就被对话面板替换掉，**旁边站着两个人时
跟其中一个说完话，另一个就从面板上消失**，想跟他说话得先按「结束对话」。

改成一级 / 二级两层：一级区（中栏）永远列着旁边所有人，正在说话的那个
只换高亮；台词、任务进度、选项挪到右栏的二级操作里。

顺带**任务进度行也从一级区拿掉了** —— 谁身上有活，地图那一格右上角的角标
已经在说；做到哪一步属于"点开才关心"的事，归二级区。
