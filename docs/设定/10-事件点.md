# 10 事件点

> 状态：骨架已定（玩法待定）
> 负责：事件点的数据结构、地图上的呈现、触发方式、触发后的去留、效果
> 不负责：事件里说什么话（见 01）、奖励给多少（见 04 / 06）、
>         任务目标怎么用事件点（见 09）、房间地形（见 05）

---

## 为什么单独一份

事件点跟 NPC 长得很像 —— 都是"地图上占一格的、带名字和字形的、有状态的东西"。
但它们**不是一回事**，混在一起写会互相污染：

| | NPC | 事件点 |
|---|---|---|
| 挡不挡路 | **挡**，走不过去 | **不挡**，可以直接走上去 |
| 怎么交互 | 站到**旁边**说话 | 走到**上面**：自动触发，或站着点按钮 |
| 状态在哪 | 态度分写在**素材**里（暂时只展示） | 触发次数写在**存档**里（会变） |
| 会不会消失 | 不会 | `once` 的会 |
| 跟任务的关系 | **发布**任务（`giver`） | 只作为任务**目标**，不发布 |
| 数据文件 | `data/npcs.js` | `data/events.js` |
| 执行模块 | `js/talk.js` | `js/events.js` |

所以分成两份文档、两个数据文件、两个模块。
**但共用一个东西**：任务的目标类型（`reach` / `use`）两种都认，见第九节。

## 一、事件点是什么

**一块地皮上的东西。** 玩家可以走上去，走上去之后可能：

- 当场发生点什么（踩到机关）—— 走上去就触发，不用按任何键
- 或者等着玩家动手（一眼泉水、地上一枚铜钱）—— 站上去之后，面板上出现一个按钮

发生完之后，它可能没了（铜钱被捡走），也可能还在（泉水一直在）。

### 三张表（都在 `data/events.js`）

一个文件里放两块数据（类型表 + 事件点表），都必须写在 `G.data` 建好之后
（即 `js/data.js` 要先加载）。

#### 1. 类型表 `G.data.eventTypes`

事件点按类型上色，并且**类型给出默认的"藏不藏"和"用完走不走"**。

| 字段 | 含义 |
|---|---|
| `id` | 类型标识 |
| `name` | 显示名，出现在「地图点位状态」面板里 |
| `color` | 地图上那个字的颜色，**同时也是那一格边框的颜色** |
| `hidden` | 可选。默认 `false`。`true` = **触发之前不画字，只画一个空框** |
| `once` | 可选。默认 `false`。`true` = 用一次就没了 |

加类型只改这里，不用碰 CSS 也不用碰 JS —— 跟 `npcTypes` 是同一个做法：
渲染时把 `color` 写成那一格上的 CSS 变量 `--event-color`，怎么用留在 CSS 里。

类型有多少种**还没定**，先放了 `spring` / `item` / `trigger` 三种，随时可以加。

#### 2. 事件点表 `G.data.events`

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | ✔ | 唯一标识，`ev_` 前缀 + 小写字母数字下划线 |
| `type` | ✔ | 类型 id，决定颜色和默认的 `hidden` / `once`，必须在 `eventTypes` 里 |
| `name` | ✔ | 名字，显示给玩家 |
| `glyph` | ✔ | **地图上画的那个字。** 跟 `name` 分开定义 —— 名字往往两三个字，格子只放得下一个 |
| `at` | ✔ | **出现位置**，一个数组，跟 NPC 的 `at` 完全同形，见下 |
| `desc` | | 站在上面时的一句描述 |
| `hint` | | **按钮上写什么字**（"喝一口" / "捡起来"）。不填用通用文案 |
| `onCollide` | | 走上去**自动**触发时的一串效果 |
| `onUse` | | 站上去**点按钮**触发时的一串效果 |
| `once` | | 覆盖类型表的 `once` |
| `hidden` | | 覆盖类型表的 `hidden` |

**`onCollide` 和 `onUse` 至少要写一个**，两个都没有的事件点什么也做不了，
`validate.mjs` 直接报错。

**没有任何"类型"字段能决定它怎么触发** —— 触发方式完全由"写了哪个回调"决定。
这条很关键，见第二节。

#### 3. 现在有哪几个

七个演示素材。前四个把**三个维度的四种组合**各占一个，后三个演示**效果怎么落地** ——
以后改素材时照着抄就行：

| id | 名字 | 位置 | 怎么触发 | 去留 | 藏不藏 | 演示的是 |
|---|---|---|---|---|---|---|
| `ev_spring` | 一眼泉水 | 大厅 (1,2) | `onUse` | 永远在 | 不藏 | 看得见，喝一口，永远在 |
| `ev_coin` | 卡住的铜钱 | 大厅 (6,4) | `onUse` | 用一次就没 | 不藏 | 看得见，抠出来，然后没了 |
| `ev_tile` | 松动的地砖 | 大厅 (2,2) | `onCollide` | 用一次就没 | 藏 | 空框，踩一下，然后没了 |
| `ev_shrine` | 墙上的石龛 | 大厅 (5,2) | **两个都写** | 永远在 | 藏 | 踩一下浮出来（之后看得见），还能再摸、再踩 |
| `ev_purse` | 遗落的钱袋 | 大厅 (7,1) | `onUse` | 用一次就没 | 不藏 | `give` 给唯一物品 + `money` 给钱 |
| `ev_note` | 摊开的笔记 | 偏厅 (2,2) | `onUse` | 用一次就没 | 不藏 | `give` 给唯一物品（笔记本） |
| `ev_herb` | 石缝里的草 | 大厅 (7,5) | `onUse` | **永远在** | 不藏 | 可重复事件点反复给可堆叠物品 |

石龛是唯一一个**两条触发路都通**的，专门用来演示
"踩下去改一下环境，之后再点一下才拿东西"。

后三个是第 22 轮（背包系统）加的，**各有各的活，别顺手删掉**：

- `ev_purse` 是**唯一同时演示 `give` 和 `money`** 的素材 —— 捡起钱袋，袋里还有十几枚钱。
- `ev_note` 是**笔记本的唯一来源**，删了就看不到任务清单了。
- `ev_herb` 是**唯一一个可重复给物品**的事件点，也是任务 `q_herb`（收集三株）的材料来源；
  它同时演示"`once: false` 的事件点每次都再给一遍东西"。

> **`take` 现在一条素材都没写。** 不是忘了 —— 现在没有任何素材需要"取走玩家的东西"，
> 而任务交付时扣物品走的是任务自己的逻辑（见 `09-NPC与任务.md` 的 `collect`），
> 不是素材里的效果。解析和校验留着别删，跟 `set` 一个道理。

`ev_note` 开在**偏厅**（`room_left`）而不是大厅，是有意的：给侧屋一点内容，
顺带演示"事件点可以开在任何房间，不只是大厅"。偏厅的地图是 6×7，
出生点 (4,3)、门在 (5,3)，(2,2) 是块空地，四条约束都满足。

### `at`：一个事件点可以出现在多个地方

```js
"at": [
  { "room": "room_hall",  "x": 1, "y": 1 },
  { "room": "room_left",  "x": 3, "y": 2 }
]
```

跟 NPC 的 `at` 是同一套规则，但**四条约束完全不同**：

- 房间必须在 `data/rooms/*.js` 里存在，坐标必须在图内
- **不能开在墙里**（`#`）—— 走不上去的东西没有意义
- **不能开在门格上** —— 门格上的动作是"进入"，再挂一个事件点两个按钮会打架
- **不能开在出生点上** —— 否则玩家一睁眼就站在上面
- **不能开在 NPC 那一格上** —— NPC 挡路，那一格玩家永远走不上去，
  事件点就成了永远碰不到的东西
- **同一个房间里同一格不能有两个事件点**

**同一个 `id` = 同一份状态。** 一个事件点写在两个房间，在 A 房间用掉了
（`once: true`），B 房间那个也没了 —— 跟 NPC「同一个人出现在多处」是同一个约定。

### 跟 NPC 长得像，但**不挡路**

`G.data.walkable()` **不算事件点**。这是整个功能的前提 —— 玩家必须能走上去。

所以 `walkable()` 跟 `npcIndex` 有关、跟 `eventIndex` 无关。
写代码时容易顺手把两者写成一样的，**这是错的**：

```js
/* 对：事件点不参与通行判定 */
walkable: function (room, x, y, npcIdx) {
  ...
  var people = npcIdx || G.data.npcIndex(room);
  if (people[x + ',' + y]) return false;    /* 只有 NPC 挡路 */
  ...
}
```

## 二、三个正交维度

事件点的行为被拆成**三个互不相干的维度**。这是这一节存在的全部理由：
不这么拆，就得写"泉水型 / 物品型 / 机关型 / 神秘型"四个并列的类型，
以后想加"踩了会响、还能再点一下"的组合就得改代码。

| 维度 | 字段 | 取值 |
|---|---|---|
| **怎么触发** | 写了哪个回调 | `onCollide`（走上去自动）/ `onUse`（点按钮）/ 两个都写 |
| **用完走不走** | `once` | `true` = 用一次就没 / `false` = 永远在 |
| **藏不藏** | `hidden` | `true` = 触发前只画空框 / `false` = 一直画自己的字 |

三个维度**可以任意组合**，组合出来的都是合法的：

| 组合 | 长什么样 |
|---|---|
| `onUse` + `once:false` + 不藏 | **一眼泉水**：看得见，点一下喝一口，永远在 |
| `onUse` + `once:true` + 不藏 | **地上一枚铜钱**：看得见，点一下捡走，然后没了 |
| `onCollide` + `once:true` + 藏 | **松动的地砖**：走上去前只有一个空框，踩下去触发，然后没了 |
| `onCollide` + `once:false` + 藏 | **墙上那个东西**：踩一下才浮出来，之后看得见，还能再踩 |
| `onCollide` + `onUse` + 不藏 | 踩一下报一次，站在上面还能再点一下 |

### 怎么触发：写了哪个回调，就有哪条路

- 写了 `onCollide` → `G.world.move()` 成功落格之后，**先**问一句这一格有没有
  要踩的东西，有就当场触发。不用玩家按任何键。
- 写了 `onUse` → 站在这一格上时，「地图点位状态」面板里多出一块，
  带一个按钮。按钮文字是 `hint`，没写就用通用文案。

**两个都写就两条路都通** —— 这一条专门用来表达
"踩下去改一下环境，之后再点一下才拿东西"。

### 用完走不走：`once`

- `once: true` —— 触发过一次之后 `G.events.alive()` 返回 `false`，
  它从地图上、从点位状态里、从触发判定里**一起消失**。不是"画成灰的"。
- `once: false` —— 永远在，**每次都再触发一遍**。反复踩反复报。

### 藏不藏：`hidden`

- `hidden: false` —— 一直画 `glyph`，玩家老远就看得见这儿有东西。
- `hidden: true` —— **触发过之前只画一个空框**：有边框、没字。
  玩家知道"这儿有东西"，但不知道是什么。触发过之后（`times > 0`）就画 `glyph` 了。

**"空框"是这一格照常画，只是不填字**，不是"不画这一格"。
所以格子大小、边框、悬停效果都跟别的格子一样，走上去也走得通。

> 实现上"不画字"画的是**一个空格**，不是空字符串 —— 这样每行的文字长度
> 还是跟列数一致（跟空地画空格是同一个道理），"每行 N 个字符"这类检查
> 才站得住。空框的边框用**虚线**，跟已经揭开的实线框一眼分得开。

判断用 `G.events.revealed(ev)`（= `!hidden || times > 0`），
**不要**在 UI 里自己写这个条件 —— 两个地方各写一遍迟早对不上。

## 三、效果（effects）

`onCollide` / `onUse` 各自是一个**数组**，每项是一条小效果，按顺序执行。

```js
"onUse": [
  { "log": "你把铜钱抠了出来，吹掉灰，塞进兜里。", "cls": "ok" }
]
```

| 键 | 作用 | 现在生效吗 |
|---|---|---|
| `log` | 往记事里写一行 | ✅ |
| `cls` | 上面那行的样式，取值跟 `G.ui.log()` 的第二参数一样：`title` / `info` / `sys` / `ok` / `warn` / `err`。不填按 `info` | ✅ |
| `give` | **给物品**，键是物品 id、值是正整数 | ✅ |
| `take` | **取走物品**，同形 | ✅ |
| `money` | **改货币**，键是币种 id、值是**带符号的字符串** | ✅ |
| `buff` | **挂一个状态**，值是状态 id | ✅ |
| `set` | **数值改动**，键是点号路径，值是**带符号的字符串** | ❌ 空壳，见下 |

**一条效果里可以同时有多个键**（"写一行 + 真的加钱"），
**一条效果也可以什么都不写**（那就是一条空效果，没意义，别写）。

物品与货币的字段定义见 `06-物品与技能.md`，状态见同一份文档的「已定：状态」。

### `give` / `take` 的写法

```js
"onUse": [
  { "log": "你捡起钱袋，掂了掂 —— 里面还有十几枚钱在响。", "cls": "ok" },
  { "give": { "itm_purse": 1 } },
  { "money": { "coin": "+12" } }
]
```

- 键是**物品 id**，值是**正整数**（数量）。`validate.mjs` 要求 id 真实存在。
- **唯一物品（`stack: false`）不许写大于 1** —— 给了也拿不到第二个，
  校验直接拦下，免得素材里留一句自欺欺人的 `"itm_purse": 5`。
- `take` 取到没有为止：身上只有 2 个却要取 5 个，取走 2 个，**不报错、不变负数**。
- 以后要"全取走"再加一个写法（比如值写 `"all"`）。现在不做 —— 没有素材需要它。

> **没给成的时候系统会补一句。** 唯一物品已经有了再给，`give` 返回 0，
> `fire()` 会往 `events` 里补一行「你已经有一个「钱袋」了。」
> （文案 `item.dup`）。
>
> 为什么要补：不补的话素材那句"你捡起钱袋"照样会写进记事，而背包里什么都没多 ——
> **这就是"静默失效"**，是本项目最讨厌的一类坑（跟 `set` 写错键、`buff` 指向不存在的状态
> 是同一类问题）。
>
> **常规情况不补。** 素材自己写的 `log` 才是给玩家看的那句话，系统不抢着再说一遍。

### `money` 的写法

```js
{ "money": { "coin": "+12" } }     // 给 12 枚
{ "money": { "coin": "-5" } }      // 花掉 5 枚
```

- 键是**币种 id**（现在只有 `coin`），值是**带符号的字符串**，跟 `set` 一个规矩。
- **不带号的一律报错**，包括 `"0"`。要写零就写 `"+0"`（但没意义，别写）。
- 扣钱**扣到 0 为止**，不会变成负数。钱不够时不会"扣失败"，
  只是实际扣掉的比要的少 —— 跟 `take` 一个规矩。

> **为什么 `money` 不并进 `give` / `take`**：货币不是物品，不占背包格
> （见 `06-物品与技能.md` 的「货币」）。混在一起会让"给东西"和"给钱"
> 共用一套键，以后做商店时反而要拆开。
>
> **也不走 `set`**：`set` 的落点是"玩家对象上的一个字段"，而货币在
> `wallet` 这张表里，两者根本不是一条路。

### `buff` 的写法

```js
{ "buff": "st_focus" }     // 挂上「凝神」
```

值是**状态 id**，必须指向 `data/statuses.js` 里真实存在的状态。

**已经挂着的状态再挂一次 = 续期**（剩余量重置回满），跟 `cast` 的行为一致 ——
不然喝两瓶药水就叠出两个「凝神」，属性明细里会多算一遍。

### `set` 的写法

```js
"set": { "player.hp": "-5", "player.ess": "-2" }
```

- 键是**点号路径**，从玩家对象出发。允许的键（`validate.mjs` 照这张表拦）：

  | 键 | 指向 |
  |---|---|
  | `player.hp` / `player.hpMax` | 生命 / 生命上限 |
  | `player.ess` / `player.essMax` | 灵性 / 灵性上限 |
  | `player.div` | 神性 |
  | `player.base.str` / `.int` / `.spr` / `.dex` / `.luk` / `.per` | 六项基础属性 |

  以后要改世界上的东西（`world.flags.xxx`）也是同一套写法，但要先把白名单扩上。
- 值是**字符串**，带 `+` 或 `-` 号，表示**增量**。
  写成 `5`（数字）不行 —— 分不清是"加 5"还是"设成 5"，`validate.mjs` 会拦下。
- **不带号的一律报错**，包括 `"0"`。要写零就写 `"+0"`。

> **为什么要把字段名列成白名单**：这个键写错了**没有任何反馈** ——
> 格式合法、校验通过、运行时又是空壳，效果永远不生效，界面上看不出来。
> 曾经的示例素材写的是 `player.gold`，而金币在 v5 已经删掉了 ——
> 这种"指向已删字段"的错就是这么溜进来的。
> 白名单只管**字段在不在**，不管**该不该改它**（后者是玩法问题）。
>
> 注意：金币在第 22 轮**回来了**，但它是 `wallet.coin`（钱包里的一种币），
> **不是 `player.gold`**。`player.gold` 仍然是错的，别写回去。

### `set` 现在一条都没写

不是"忘了"，是**没有合法的目标字段**：

- `04-数值与成长.md` 定了**生命 / 灵性只做显示**，唯一能自动改它们的是状态的 `tick`；
- 六项基础属性和神性是角色自己的东西，事件点不该直接去改。

所以现在几个事件点都只写 `log` / `give` / `money`。**但解析和校验这两条路留着别删** ——
等 A 组拍板、真有了能改的字段，素材直接写上就生效，代码一行都不用动。

> 冒烟里有一条专门盯这个：它**临时**造一个带 `set` 的事件点，
> 确认 `G.events.fire()` 真的会去调 `applyEffect`（只是不改数值），验完立刻收拾干净。
> 别为了测试往 `data/` 里塞假素材。

### 效果分三条路落地

`fire()` 遍历效果项，按**写了哪个键**分派到不同的落点：

| 键 | 落到哪 | 现在真做吗 |
|---|---|---|
| `log` / `cls` | 直接变成 `events` 里的 `{ text, cls }`，调用方拿去写记事 | ✅ |
| `give` / `take` / `money` | `G.items`（背包与钱包） | ✅ |
| `buff` | `G.statuses`（挂状态） | ✅ |
| `set` | `G.rules.applyEffect` | ❌ 空壳 |

> **`set` 是唯一还没接通的一条**，因为它是唯一一个"目标字段还没定"的。
> 别把 `give` / `money` 也塞进 `applyEffect` —— 它们的落点不是玩家对象上的字段，
> 而是一张表（`items` / `wallet`），塞进去那个函数就变成什么都管了。

### 但 `set` **现在不真改数值**

`G.rules.applyEffect(key, delta)` 是个**空壳**，直接返回 `false`，什么都不做。

原因：玩法还没定 —— 终点、时长、战斗、死亡处理全在 `99-待定问题.md` 的 A 组挂着，
**连"有没有血量"都还没定**。现在就把扣血逻辑写实，等于替玩家把一个还没拍的板拍了。

所以现在的做法是：

1. **素材里暂时一条 `set` 都不写** —— 上面说了，现在没有合法的目标字段
2. **`G.events.fire()` 照常解析、照常调 `applyEffect`**（这条路径有测试盯着，见上）
3. **`applyEffect` 什么都不做**

等玩法定了，**只改 `applyEffect` 这一个函数**，素材一行都不用动 ——
在那之前，事件点里写数值效果是"记在案上但暂时不生效"。

> ⚠️ 这条约定要一直留着，直到 A 组拍板。别因为"反正没效果、反正没素材写"就把
> `set` 的解析或校验删掉 —— 删了以后加回来时，素材里写错的键就没人拦了
> （`player.gold` 那种错就是这么溜进来的）。
>
> **`give` / `take` / `money` / `buff` 不受这条影响** —— 它们四条路都已经接通了，
> 素材里写上就真的生效。只有 `set` 一条还在等 A 组。

## 四、地图上怎么画

| 情况 | 画什么 | 类名 |
|---|---|---|
| 站在这一格 | `glyph`，颜色取自类型的 `color` | `event` |
| `hidden` 且**没触发过** | **一个字都不画**，只留边框 | `event hidden` |

- **画的是 `glyph`，不是 `name`。** 这是这个字段存在的全部理由。
- 满宽汉字照 `--fs` 那么大会贴着格子边，所以事件点那一格的字**单独缩到 0.7**
  （跟门格、NPC 一样的处理）。
- **边框用类型色。** 跟玩家格的绿框、NPC 的类型色框同一个做法：`inset` 阴影画的，
  **不占布局**，格子宽高不会被挤动。颜色走 `--event-color` 变量，改类型表就换色。
- **空框的边框要比正常的淡**，一眼能分出"这儿还没揭开"和"这儿是什么"。
  具体淡到什么程度留在 CSS 里。

画法的优先级：**玩家 > NPC > 事件点 > 门 > 墙 > 空地**。

- 玩家跟事件点**可以同格**（事件点不挡路），所以玩家必须排在前面 ——
  玩家站在泉水上时，那一格画的是玩家的名字首字，不是「泉」。
- NPC 跟事件点、事件点跟门格，`validate.mjs` 都拦下了，顺序只是保险。

## 五、一级区里怎么显示

**只有站在事件点那一格上时才显示** —— 跟门一样，"动作属于哪个东西，
按钮就跟着那个东西出现"。没站在上面时这一块根本不存在。

> 事件点这一块是**一级**的：它直接讲"脚下这一格有什么"，就画在中栏
> 「地图点位状态」里，跟门、跟「旁边的人」并列。二级操作（右栏那块）
> 现在只放对话，事件点暂时用不上它。一级 / 二级的分工见
> `02-玩法循环与操作.md`。

```
地上
一眼泉水                     ← 用类型的颜色
泉水                         ← 类型名
石缝里渗出一小汪水，清得能看见底。  ← desc（没写就不画这一行）
[  喝一口  ]                 ← 按钮，文字是 hint（没写用通用文案）
```

- 标题叫「**地上**」而不是「脚下」—— 「脚下」那一行已经被占用了
  （讲的是"这一格是空地还是门"），两行都叫"脚下"会看串。
- 名字用类型色，颜色来自数据表，`ui.js` 只负责搬运。
- **`desc` 没写就不画那一行**，不是画一行空的。
- **按钮只在有 `onUse` 的时候画。** 纯 `onCollide` 的事件点没有按钮 ——
  它的动作是"走上去"，玩家已经走上去了，再给个按钮是多余。
- **已经用掉的一次性事件点不显示这一块** —— `G.events.at()` 已经过滤过了，
  根本不会返回它。

### 进房间时提一句？

**不提。** 事件点是"看一眼地图"的事，写进日志反而要玩家自己对照坐标
（跟 NPC 的处理不一样：NPC 挡路、会发布任务，属于"这屋里有谁"的信息）。

## 六、指令 `use`

| 指令 | 作用 |
|---|---|
| `use` | 互动脚下的东西。别名 `互动` / `用` |

- **不出现在操作区里**，跟 `enter` / `talk` 一样 —— 它绑在事件点上，
  没站在事件点上时那个按钮根本不存在。
- `quiet: true`：按钮和键盘触发的都不回显；手打的仍然回显。
- 站在空地上打 `use`：记事说一句"脚下没有可以互动的东西"。
- 站在纯 `onCollide` 的事件点上打 `use`：说一句中性的话
  （"你碰了碰，没什么反应"），**不暴露"这个要用脚踩"这种机制**。

**走路模式不受影响**：`use` 只有打字或点按钮两条路，没有键位。

## 七、状态存储

存在存档的 `events` 字段里，形状是 `事件点 id -> { times }`：

```json
"events": {
  "ev_coin": { "times": 1 },
  "ev_spring": { "times": 7 }
}
```

| 字段 | 含义 |
|---|---|
| `times` | 触发 / 互动过几次 |

**只记次数，不记布尔。** 一个 `times` 同时能回答三个问题：

- `once` 的"用掉了没有" → `times > 0`
- `hidden` 的"揭开没有" → `times > 0`
- 可重复的"踩过几回了" → `times` 本身（以后要做"第三次来的时候换句话"就用它）

记布尔的话，前两个问题要两个字段，第三个还要再加一个。

**"没有记录" = 一次都没触发过。** 所以旧存档（连 `events` 字段都没有的）
读进来，所有事件点都是初始状态，不用迁移数据 —— 跟 `quests` 是同一个约定。

### 存档版本 v3 → v4

`G.state.VERSION` 从 3 升到 4，`create()` 加一个空的 `events: {}`，
`normalize()` 加 `events: raw.events || {}`，`migrate()` 补一段：

```js
/* v3 → v4：加了事件点的触发次数。补个空对象就行 ——
   "没有记录" = 一次都没触发过，正好是想要的效果。 */
if (v < 4) { raw.events = raw.events || {}; }
```

## 八、模块 `js/events.js`（`G.events`）

**不碰 DOM。** `ui.js` 要读它来画地图（`ui → events`），
所以它不能反向调 `ui` —— 否则两个模块成环，违反"依赖方向严格单向"。
按项目的做法：`fire()` 只**产出事件列表** `{ text, cls }`，
调用方（`main.js` 的 `runUse`、`world.js` 的 `move`）负责写记事和刷新。

| 接口 | 作用 |
|---|---|
| `alive(ev)` | 这个东西还在不在（`once` 且用过 → `false`） |
| `revealed(ev)` | 该不该画字（不藏，或者触发过） |
| `once(ev)` / `hidden(ev)` | 取"条目覆盖类型表"之后的实际值 |
| `index(room)` | 这一房间的 `{ "x,y": ev }` 索引，**只含还活着的** |
| `at(room, x, y)` | 站在这一格上的事件点，没有返回 `null` |
| `times(id)` | 触发过几次 |
| `fire(ev, kind)` | 触发。`kind` 是 `'step'` 或 `'use'`，返回 `{ ok, events }` |

`fire()` 的返回值：

- `ok` —— 真的触发了。**没触发**有三种情况：事件点不存在 / 已经用掉了 /
  这种触发方式它没写回调（比如拿 `'use'` 去点一个纯 `onCollide` 的东西）
- `events` —— 要写进记事的行，`[{ text, cls }]`。
  **跟 `G.talk` 的返回值字段同名**，因为调用方的处理方式一模一样。

`events` 里绝大多数行来自素材的 `log`，但**也可能有系统补的**：
唯一物品重复获得时会补一句 `item.dup`（见上面「没给成的时候系统会补一句」）。
调用方不需要区分这两种 —— 都是"要写进记事的一行"。

`fire()` 内部顺序：**先记次数，再跑效果**。反过来的话，
效果里如果又想问一次"这是第几次"，拿到的还是旧值。

**"取条目覆盖类型表"的逻辑只写一遍**（`once()` / `hidden()` 两个函数），
别在 UI 里再抄一遍。

### 谁调 `fire()`

| 触发方式 | 调用点 | 时机 |
|---|---|---|
| `step` | `G.world.move()` | 成功落格、打完"你向上走了一步"之后 |
| `use` | `G.world.useAt()` | 玩家打 `use` 或点按钮 |

`move()` 里的顺序是：**落格 → 对话断开 → 门提示 → 事件点触发 → 走路任务 → 刷新 → 存档**。

事件点放在"走路任务"**前面**：踩到机关说一句，比"任务目标达成"更贴近刚发生的事。

## 九、跟任务的关系

任务的 `goal.type` 加两种，两种都认事件点：

| 目标类型 | 什么时候推进 |
|---|---|
| `reach` | 走到指定事件点那一格上（`step` / `use` 都算） |
| `use` | **互动**指定事件点（点按钮或打 `use`） |

`reach` 和 `use` 的区别：**站在泉水上是 `reach`，喝一口才是 `use`。**

任务的 `goal` 里用 `ev` 指定是哪一个事件点：

```js
"goal": { "type": "reach", "count": 1, "ev": "ev_spring" }   走到那眼泉水
"goal": { "type": "use",   "count": 1, "ev": "ev_spring" }   在那儿喝一口
```

**`reach` / `use` 必须写 `ev`**，`walk` 不用（它不挑地方）。`validate.mjs` 强制检查，
而且 `ev` 必须指向真实存在的事件点。

#### 推进走的是另外两个入口，不是 `add()`

| 入口 | 什么时候调 | 推进多少 |
|---|---|---|
| `G.quests.reach(evId)` | `world.move()` 落在事件点上 | **直接置满** —— 一个事件点不存在"走到一半"这种事 |
| `G.quests.use(evId)` | `world.useAt()` 互动成功 | 步进 1（可重复互动的事件点，任务可能要"用三次"） |

两个都**只推进已经接取的任务**（未接收不可执行），
也都**返回"这一次刚刚达成目标"的任务数组** —— 跟 `add()` 一致，调用方拿去打日志。

为什么不并进 `add()`：`add()` 只需要知道"走了/杀了/捡了"，
而"走到某个**特定**事件点上"必须知道是哪一个。硬塞进去就得给它加可选参数、
还得在里面判断有没有传，反而更难读。

两个入口都要求 `goal.ev` **就是那个 id** —— 所以同一个 `reach` 任务
不会因为走到别的事件点上就完成。

> ⚠️ **走到就算"到了"，跟触发成没成功无关。**
> 泉水只有 `onUse`，踩上去 `fire()` 返回 `ok: false`（没有 `onCollide` 可跑），
> 但玩家确实走上去了，`reach` 该算数。
> `fire()` 的 `ok` 只表示"这次有没有触发效果"，**不是"玩家有没有到"**。
> 这两件事混起来会让"走到泉水边"这种任务永远做不完。

**事件点不发布任务。** 它没有 `giver`，也不参与 `ofNpc()`。
想让它"发布"任务，那是 NPC 的事，事件点顶多是个目标。

## 十、素材完整性（强制）

下面这些由 `tools/validate.mjs` 强制检查，**写错直接报错**，不会等到运行到一半才炸。

**类型表：** `id` / `name` / `color` 必填，`id` 不能重复，
`hidden` / `once` 若填了必须是布尔。

**事件点表：**

- `id` 带 `ev_` 前缀、`name` 必填
- **`glyph` 必须正好是一个字**（`Array.from` 算长度，表情符号也算一个）
- `type` 必须能在类型表里找到
- **`onCollide` / `onUse` 至少要有一个**，写了的必须是**非空数组**
- 每一项效果的键只能是 `log` / `cls` / `set` / `give` / `take` / `money` / `buff`
  里的，**出现别的键直接报错**（打错一个字母就等于这条效果静默失效，必须拦）
- `log` 若填了必须是非空字符串；`cls` 若填了必须在样式白名单里
- **`set` 的键必须是 `player.` 开头的点号路径，值必须是带 `+` / `-` 号的字符串**
- **`set` 的键还必须指向玩家对象上真实存在的字段**（见下面的白名单）。
  只校验格式是不够的：写成已删字段（`player.gold`）格式完全合法，
  而 `applyEffect` 又是空壳，于是这条效果**永远静默失效**、界面上一点都看不出来。
- **`give` / `take` 的键必须指向真实存在的物品**（`data/items.js`），
  值必须是正整数；**唯一物品（`stack: false`）的值不许大于 1** ——
  给了也拿不到第二个，校验直接拦下，免得素材里留一句自欺欺人的 `"itm_purse": 5`。
- **`money` 的键必须指向真实存在的币种**（`G.data.moneyTypes`），
  值必须是**带符号的字符串**（跟 `set` 一个规矩，`"+0"` 合法、`0` 不合法）。
- **`buff` 的值必须是真实存在的状态 id**（`data/statuses.js`）。
  这个写错了**没有任何反馈**：挂不上任何状态，记事里也不会说一句，
  界面上完全看不出来 —— 跟 `set` 是同一类坑，必须拦。
- `once` / `hidden` 若填了必须是布尔
- `hint` / `desc` 若填了必须是非空字符串
- **`at` 必须是非空数组**；每一项的房间必须存在、坐标在界内、
  **不在墙里**、**不在门格上**、**不在出生点上**、**不在 NPC 那一格上**
- **同一个房间里同一格不能有两个事件点**

**事件点不参与"路通不通"的检查。** 它不挡路，堵不死任何东西 ——
`validate.mjs` 里那条从出生点做的 BFS 只算 NPC。
