# 08 技术约束

> 状态：已定
> 负责：平台限制、代码组织、编码约定、构建与交付
> 不负责：任何玩法与数值

---

## 交付形态

- **开发期**：多文件，双击 `index.html` 直接跑，改完刷新即可。
- **交付期**：`node tools/build.mjs` 把样式、脚本、数据全部内联，产出单个 HTML。
- 压缩包或微信直发都只发这一个文件，对方存桌面双击即玩。

为什么坚持单文件交付（即使多文件在 `file://` 下也能跑）：

1. 不用解压。从压缩包里直接双击，Windows 会先解到临时目录，路径每次都不同。
2. 不会因为漏发某个 js 文件而白屏。
3. 一个文件可以直接发微信 / QQ。

---

## 四条硬规则

1. **不用 ES Module。** `import` / `export` / `type="module"` 加载外部文件，在 `file://` 下全部报 `Failed to fetch`。改用普通 `<script src>` + 全局命名空间。
2. **数据文件是 `.js`，不是 `.json`。** `fetch` 本地 json 会抛 `TypeError`。写成 `G.data.monsters = [ ...纯 JSON 字面量... ];`，内部仍是严格 JSON，校验脚本剥掉前缀后照旧 `JSON.parse`。
3. **开发环境 = 交付环境 = `file://`。** 不允许出现"开发时用服务器所以能跑、发出去就炸"的情况。
4. **所有文件 UTF-8 无 BOM**，HTML 显式声明 `<meta charset="utf-8">`。构建脚本加一道编码检查，防止被编辑器存成 GBK——GBK 文件在本机看着正常，发给别人就乱码。

---

## 代码组织

- 每个 js 文件一个 IIFE，把自己挂到全局 `G` 上：`G.rng = (function () { ... })();`
- 加载顺序即依赖顺序，写在 `index.html` 里。
- 依赖方向严格单向，不允许成环。
- 逻辑与表现分离：产出事件列表的模块不碰 DOM。

### 模块清单与加载顺序

**加载顺序即依赖顺序**，写在 `index.html` 里，不允许调整：

```
js/rng.js       G.rng     种子随机（mulberry32），可存取游标
js/rules.js     G.rules   属性表、生命惩罚、属性合成公式、初始角色、名字校验、态度阶段映射
js/data.js      G.data    数据容器与按 id 查询（区域、房间、格子、门、NPC、任务、事件点、技能、状态、物品、币种）
data/strings.js G.data.strings  界面文案
data/areas.js   G.data.areas    区域表
data/rooms/*.js G.data.rooms    房间与门，**一个区域一个文件**
data/npcs.js    G.data.npcTypes / attitudeStages / npcs    NPC 类型、态度阶段、NPC 本体
data/quests.js  G.data.quests   任务定义
data/items.js   G.data.itemKinds / moneyTypes / items     物品分类、币种、物品本体
data/events.js  G.data.eventTypes / events   事件点类型表、事件点本体
data/skills.js  G.data.skills   技能表
data/statuses.js G.data.statuses 状态表
js/state.js     G.state   状态结构、序列化、版本迁移
js/items.js     G.items   背包与钱包：有几个、给、取、用、查余额（不碰 DOM）
js/save.js      G.save    本地存储 / 磁盘文件 / 导出导入
js/quests.js    G.quests  任务进度（只推进，不含任务定义）
js/talk.js      G.talk    对话：正在跟谁说话、说了哪一句、能选什么（不碰 DOM）
js/events.js    G.events  事件点：还在不在、该不该画字、触发一次会怎样（不碰 DOM）
js/skills.js    G.skills  技能：拥有哪些、被动修正、用一个主动技能（不碰 DOM）
js/statuses.js  G.statuses 状态：挂摘、按步计时、收集修正、灵性阈值自动挂摘（不碰 DOM）
js/ui.js        G.ui      记事、地图、玩家状态与状态、背包、地图点位状态、操作区、弹框、创建角色页、输入栏
js/world.js     G.world   房间查询、移动、进门、描述
js/main.js      —         指令表、键盘分发、走路/命令模式、引导、角色创建、指令分发（唯一入口）
```

`data/items.js` 一个文件里放**三块数据**（分类表 / 币种表 / 物品表），
跟 `data/npcs.js` 一样走 `loadTop()`；`validate.mjs` 的取值函数必须**按配对括号切**，
不能从 `=` 一直切到分号（见文末「改 `validate.mjs` 前必看」第 2 条）。

`js/items.js` 是**唯一读写背包与钱包**的地方 —— `js/events.js`（效果）、
`js/quests.js`（`collect` 目标与奖励）、`js/ui.js`（画背包、画钱包、画笔记本）
都调它，谁都不自己去翻 `G.state.data.items` / `wallet`。

`data/skills.js` 和 `data/statuses.js` 跟房间素材一样用 `G.data.x.push(...)` 追加，
所以 `js/data.js` 必须排在它们前面（它负责先把 `G.data.skills` / `G.data.statuses` 建出来）。
`validate.mjs` 里读这种文件的函数是 `loadPushed()`，跟读 `G.data.x = [...]` 的 `loadTop()` 分开。

**技能与状态同样是"不碰 DOM、只产数据"**：`skills.use()` 只返回
`{ ok, skill, status, refreshed }`，`statuses.tickStep()` 只返回
`{ ticks, expired }`，写记事与刷新由调用方（`main.js` 的 `doCast`、`world.js` 的 `tickStatuses`）负责。

`data/npcs.js` 一个文件里放**三块数据**（类型表 / 态度阶段表 / NPC 表），
所以 `validate.mjs` 的取值函数必须**按配对括号切**，不能从 `=` 一直切到分号 ——
那会把后面两块一起吞进来，报一个位置对不上的 JSON 解析错误。

`data/quests.js` 只有任务**定义**；进度在 `js/quests.js`。
分开是因为进度要读写存档，定义不用 —— 混在一起会让"定义"和"存档"两个概念黏住。

`ui` 只被 `main` 调用；`world` 不碰 DOM。以后加战斗时，`combat.js` 插在 `ui` 与 `world` 之间，同样只产出事件列表。

`talk` 也**不碰 DOM**，而且**不能反向调 `ui`** —— `ui` 要读对话状态来画面板（`ui → talk`），
反着调就成环了。所以 `talk` 只**产出事件列表** `{ text, cls }`，
调用方（`main.js` 的 `runTalk`）负责拿去写记事和刷新。

`events` 跟 `talk` 是同一条规矩：**不碰 DOM**，`fire()` 只产出
`{ ok, events }`（`events` 是要写进记事的行），调用方（`world.js` / `main.js`）负责落日志与刷新。

> `events` 和 `talk` 的返回字段同名（都叫 `events`），因为它们处理方式一模一样。
> 读的时候注意 `G.events.fire().events` 是"记事行"，不是"事件点"。

**事件点不参与通行判定。** `walkable()` 只查 `npcIndex`，
**永远不要把事件点也加进去** —— 玩家必须能走上去，这是整个功能的前提（见 `10-事件点.md`）。

`ui` 内部只负责"把状态画出来"，不含任何规则判断；`main` 的 `CMDS` 是指令的唯一事实来源，
输入框、操作区按钮、键盘、点地图四条路都从它出发，加指令只改一处。

`ui` **不反向调 `main`**。比如点地图格子走路：`ui` 只负责把"这个方向能走"标在格子上
（`data-move`），谁被点到了怎么处理由 `main` 决定。

**弹框（模态浮层）也归 `ui`。** "现在开着哪个弹框"是**纯外观状态**，
跟"走路模式 / 命令模式"不一样（那个归 `main`，因为它管按键归属）。
`ui` 自己存着当前弹框，对外开两个口子给 `main` 用：
`G.ui.modalOpen()` 让 `main` 决定"键盘还给不给游戏"，
`G.ui.closeModal()` 让 `main` 处理 Esc 和点遮罩。
弹框里的按钮**照样是 `button[data-cmd]`** —— `main` 那个全局点击委托本来就认这个，
所以弹框里不用另写一套点击处理。

> 弹框里的按钮带 `data-cmd` + `data-arg`（比如 `cast` + `skl_focus`），
> 点下去走的是跟操作区按钮完全同一条路 —— 这是"四条路走同一张指令表"的好处：
> 新加一层 UI 不用新加一套分发。

**`save` 不反向调 `main`。** 它读档 / 导入完只调 `G.ui.refresh()`，就这一处出口。

> 这里踩过的坑：`load()` / `onImportFile()` 原来只调 `G.ui.refresh()`，
> 而 `refresh()` **不含 `renderActions`** —— 那时候操作区有一组按"拥有哪些主动技能"
> 现生成的按钮，于是导入一份技能集不同的存档之后，操作区还挂着上一个角色的
> 「凝神」按钮，点下去报"没有这个指令"。
>
> 当时为了不破坏依赖方向，加过一个注册口子：`main` 在 `init()` 里
> `G.save.onLoaded(fn)` 把"读档后要做的事"挂进去，`save` 读档完挨个调一遍。
>
> **那个口子后来删掉了。** 因为「技能」分组本身废弃了 —— 改成「行动」组里
> 一个固定的「释放法术」按钮（见 `06-物品与技能.md`），操作区的内容
> **跟角色完全无关**，读档之后一个按钮都不会变，也就没有"要重画"这回事。
> 挂着一个没人用的注册口子等于留了个没人看的坑，所以连 `afterLoad` /
> `onLoaded` / `runAfterLoad` 三个函数一起删了。
>
> **教训**：`refresh()` 不含某块渲染这件事本身没错 —— 错的是"有块界面会随角色变、
> 却没进 refresh"。与其加一层注册绕开，不如先问"这块内容真的需要随角色变吗"。
> 冒烟里现在有一节「操作区不随角色变化」盯着这条，防止哪天又长出动态组来。

**房间素材一个区域一个文件**（`data/rooms/<区域 id>.js`），文件里用
`G.data.rooms.push(...)` 往房间表里追加。所以 `js/data.js` 必须排在它们前面 ——
它负责把 `G.data.areas` 和 `G.data.rooms` 先建出来，否则 push 的目标还不存在。

新增一个区域文件后，**记得在 `index.html` 里补一行 `<script src>`**：
`tools/build.mjs` 是照 `index.html` 里的标签内联的，不补就不会被打进产物，
而开发环境（`file://` 直接开 `index.html`）也是照同一份清单加载 —— 一处漏了就两边都漏。
`tools/validate.mjs` 反过来是**扫描整个 `data/rooms/` 目录**，不写死文件名，新文件自动纳入校验。

## 验证（交付前必跑）

```bash
# 1. 素材
node tools/validate.mjs

# 2. 开发版冒烟：真的把游戏跑一遍
node tools/probe.mjs "file:///D:/魔鱼世界/index.html" tools/smoke.js

# 3. 反向验证：故意把关键规则改坏，确认冒烟真的拦得住（会自动还原）
node tools/mutate.mjs

# 4. 打包
node tools/build.mjs

# 5. 产物复验 —— 这一步过了才算能交付
node tools/probe.mjs "file:///D:/魔鱼世界/dist/魔鱼世界.html" tools/smoke.js
```

`smoke.js` 覆盖逻辑、界面渲染、布局、键盘与模式、上下文按钮、区域归属、
NPC 与任务、对话、一级区 / 二级操作、玩家状态与状态、技能与状态的边角、
事件点、门、存档往返、操作区不随角色变化、弹框、物品与背包、收集任务与奖励、
降级容错，共 762 项。
**渲染是单独验的**：逻辑对了不等于画对了，两条是不同的代码路径。
**布局也是单独验的**：这里量的是真实外框（`getBoundingClientRect`），不是"元素存不存在"。
第一版骨架就因为状态面板被裁而全程绿灯，截图才发现。

**断言别写成恒真的。** 第一版验"操作区按内容高度、没被拉伸"时写的是
`scrollHeight <= clientHeight` —— 而 `scrollHeight` **永远** ≥ `clientHeight`，
这条断言怎么改代码都是绿的，等于没写（反向验证时才看出来：破坏之后它没变红）。
换成量**里面那几组按钮实际占多高**（首尾两个 `.group` 的外框之差）才拦得住。
**写完一条断言，先想想"它在什么情况下会红"** —— 想不出来就是白写。

**点按钮的辅助函数找不到元素时不能抛错。** 冒烟里点面板按钮一律走
`clickArg` / `clickCmd` / `clickMove` 这几个小包装：找不到就返回 `false`，
让对应的那条断言变红就行。直接 `.click()` 会在元素不存在时抛 `TypeError`，
整个脚本中途炸掉，**后面的检查一条都不跑**，报出来的错还指不到真正的问题
（改坏 `deliver()` 做反向验证时踩过一次）。

**反过来，这几个包装会真的点下去，不能当查询用。**
`T('面板上有按钮', !!clickCmd('use'))` 会把一次互动提前消耗掉，
后面一串断言跟着错（加事件点那次踩过）。断言"按钮在不在"用 `hasCmd(cmd)`。

**断言里不要直接访问可能不存在的深层字段**（`G.state.data.events.ev_spring.times`）。
上面某一步没走到时这里会抛 `TypeError`，同样把后面几十条检查全带走 ——
走 `G.events.times('ev_spring')` 这种有兜底的查询。

**取元素的 class 也别写成 `(el || {}).className.indexOf(...)`。**
元素不存在时 `{}.className` 是 `undefined`，`.indexOf` 照样抛错，
后面几十条检查一起完蛋（反向验证时逮住的：那条破坏本来该变红十几条，
结果只报了个"求值抛错"）。冒烟里统一走 `clsOf(el)`，元素不在就返回空串。

**改 CSS 的共用选择器要格外小心。** `#tile, #secondary dd.act button` 看着像
"两块面板里的按钮"，其实是**两条选择器**：裸的 `#tile`，和 `#secondary dd.act button`。
结果规则落到整个 `dl` 上，`#tile` 里的按钮一条都没选到 —— 门那个「进入这扇门」
按钮的颜色和宽度一起丢了。要"两块面板"就写 `:is(#tile, #secondary) xxx`。
**这种错逻辑测试一条都发现不了，是冒烟里那两条量颜色、量宽度的检查逮住的** ——
所以界面相关的检查别嫌它琐碎。

**写完新检查要故意写坏一次，确认真的会拦。** 冒烟测试最容易出的问题是
"断言写得太松，代码改坏了它照样绿"。所以每加一组检查，都先把对应逻辑
改坏（改字形、改边界、把推进调用删掉……），确认失败数对得上，再改回来。

这件事已经脚本化了：`node tools/mutate.mjs` 会照着 `tools/mutate.mjs` 里那张
**破坏清单**（现在 58 条）逐条改坏 → 跑冒烟 → 数变红的条数 → **立刻还原**
（在 `finally` 里还原，中途报错也还原）。新加一组检查时，往清单里补一条对应规则的破坏点。

> ⚠ **它要跑几分钟，别用会超时的前台命令跑。** 被 `kill` 掉时 `finally` 不执行，
> 那个正在改坏的文件就**留在改坏状态**了 —— 之后所有验证结果都不可信，
> 而症状只是"某条断言一直红" + "清单里那条被跳过"，很难联想到是它。
> 现在脚本挂了 SIGINT / SIGTERM / SIGHUP 处理器，收到先还原再退出；
> 跳过的提示里也写明了"可能是上一次被中途杀掉"。
> **跑之前先确认工作区是干净的**（`validate` + 冒烟都能过）最稳妥。

**清单里有两种判据，别混：**

| 判据 | 怎么写的 | 看什么 |
|---|---|---|
| 改坏代码，等冒烟变红 | 默认 | 输出里 `✗` 的条数 |
| 塞坏素材，等 validate 报错 | 加 `expect: '那句话'` | 输出里有没有那句话 |

**第二种是必须的，不是可选的花样。** 校验类规则用第一种**验不出来**：
把 `validate.mjs` 里某条检查删掉，结果是"校验通过了" ——
一个"通过"里数不出任何 `✗`，脚本会报"没有任何断言变红"，
看着像拦住了，其实什么也没验到（写这一轮时真的这么撞了一次）。
**校验的判据只能是"坏素材必须被报出来"。**

两条注意：破坏点要挑**不会让冒烟脚本中途抛错**的（炸在半路后面的检查一条都不跑，
看着"拦住了"其实什么也没验到）；清单里的代码片段会随重构失效，
脚本遇到找不到的片段只警告、不硬失败。

> **破坏点变红 ≠ 它锁的规则被拦住了。** 变红的可能是**别的**断言 ——
> 尤其工作区里还残留着上一次没还原的改动时，会有一条断言常年红着，
> 于是**每一条破坏点都"拦住了"**，整张清单等于全废（这一轮真撞上过：

### 改验证脚本前必看

1. **求值前必须等 `document.readyState === 'complete'`。** 否则会撞上解析竞态，拿到 null 或脚本还没执行。
2. **不要用 `--virtual-time-budget` 配合 `setTimeout` 做超时兜底。** 虚拟时钟会把定时器提前触发，产生假阴性（IndexedDB 就这样被误判过一次）。
3. **测试自己也会写错。** 曾经因为「读档后取随机数应等于读档前那个」报了假失败——`next()` 是先推进游标再取值，读档后取到的必然是紧接着的下一个数。
4. **量布局要量实际渲染出来的外框（`getBoundingClientRect`），不要拿 `line-height` 跟字宽比。** 那样量到的是"字符盒"的比例；等宽字形本身高瘦，怎么比都不是正方形。曾经据此写出的"正方形断言"在实现已经正确时仍然报失败。
5. **测别名要挑走得动的位置。** 在贴着墙的格子上测方向别名，会误判成失败——先走回空地再测。
6. **视口要用 `Emulation.setDeviceMetricsOverride` 锁死，不能只给浏览器传 `--window-size`。** 无头模式下视口常常跟它对不上，截图尺寸会飘（曾经两种窗口尺寸截出来是同一张图），宽屏布局根本测不到。
7. **量可用空间要用 `clientWidth / clientHeight`，不要用 `getBoundingClientRect()`。** 前者扣掉了滚动条，后者不扣。用后者会陷入"出现滚动条 → 可用宽度变小 → 还是溢出"的死循环。
8. **不要靠 `focus` / `blur` 事件做逻辑判断。** 无头浏览器里文档没有焦点，Chrome 会把这两个事件推迟派发，测不到。所以：键盘行为看 `document.activeElement`，焦点相关的外观用 `mousedown` 这类一定会派发的事件触发。
9. **测键盘要派发真的 `KeyboardEvent`，并同时给 `code` 和 `key`。** 处理函数按 `code`（物理键位）认键，按 `key`（字符）认 `/` 和回车，少给一个就测不到。
10. **拿不准就写探针量，别看截图猜。** 截图会被缩放、被相邻格子的元素干扰，
    一眼看过去很容易把两个格子的东西看成一格。量 `getBoundingClientRect()` 和
    `getComputedStyle(el, '::after')` 才是准的 —— 曾经据此差点误判"角标画错了格子"。
11. **断言要先把"前提"造出来，否则它在某些窗口尺寸下是恒真的。**
    验"选项多到装不下时滚到底能不能看全最后一个"时，宽窗口下面板有 390px、
    三个选项怎么都装得下 —— 这条在 1440×860 下永远绿，等于没写。
    改成**临时把面板压矮**（`style.maxHeight = '90px'`，量完还回去）把前提造出来，
    两种窗口下就都在真的验滚动了。
    **同一个道理：前提要显式摆，别假设前面某一步已经把它摆好了。**
    验"进门不推进走路任务"时，我以为 `q_walk20` 那时候已经接了 ——
    其实它只是"可接"，没接的任务压根不推进，于是断言怎么改代码都绿。
    先 `G.quests.accept()` 真的接下来（验完把记录整个还原），前提才算真的成立。
12. **别拿 0.5px 的容差量"滚到底看不看得全"。** `scrollHeight` 是**取整**的：
    内容真实高度 193.5、`clientHeight` 190 时，`scrollTop` 最多只能到 3，
    最后那 0.5px 永远滚不出来 —— 那是取整残差，不是"被裁掉"。
    容差留到 2px，并且**量"露出来多少"**（可见区和按钮的重叠高度 ≥ 按钮高度 − 2），
    而不是量"按钮底边跟容器底边差几个像素"。1100×700 下就被这 0.03px 卡红过。
    另外这条还**跟台词长度有关**（台词随机挑，长短决定折几行）——
    同一份代码连跑三遍两红一绿，是典型的"断言前提没锁死"。
13. **验"还原成功"时要断言字面量，别拿变量跟它自己的副本比。**
    临时改素材再还原时，写成 `const saved = obj.x; obj.x = 'x_nope'; ... obj.x = saved;
    T('还原了', obj.x === saved)` —— 这条是**恒真**的，等于没验（而且还会掩盖
    "我记错了原值是什么"）。要断言 `obj.x === '真实值'`。
    同一次还踩了另一半：那个"真实值"我当时写成了**技能 id**，
    而 `applies` 里存的是**状态 id**（`skl_focus.applies === 'st_focus'`），
    于是断言恒红。**名字里带 `skl_` / `st_` 的字段要看清它该装哪一种。**

### 改 `validate.mjs` 前必看（解析素材的三个坑）

素材是 `.js` 不是 `.json`，校验脚本得先把赋值前缀剥掉再 `JSON.parse`。踩过三次：

1. **找 `G.data.x =` 必须要求"标记后面紧跟等号"。**
   先找标记、再找下一个等号，会被**文件头注释里**的等号骗到，
   从注释中间切开，报出来的错跟真正的问题八竿子打不着。
2. **一个文件可以放好几块数据**（`data/npcs.js` 有三块）。
   切值不能"从 `=` 一直切到分号"，要**扫一遍括号配平**、只取配对的那一对，
   否则会把后面几块一起吞进来，报 `Unexpected non-whitespace character after JSON`。
3. **`push(a, b, c)` 是多个参数，不是数组。** 切出来的 body 按 JSON 解析前要自己补一对方括号；
   切括号范围时**不能取最后一个 `)`**（注释里出现一个括号就切歪了），同样要扫括号配平。

另：切括号时要**跳过字符串字面量里的括号**，否则 `"（"` 这种全角/半角混排的文案会把配平算错。

**两种写法配两个读函数，别混用**（曾经因为用错踩过）：

| 写法 | 用哪个 | 现在谁在用 |
|---|---|---|
| `G.data.x = [ ... ];` | `loadTop(rel, name)` | strings / areas / npcs / quests / events |
| `G.data.x.push( {...}, {...} );` | `loadPushed(rel, name)` | rooms/*.js、skills.js、statuses.js |

`loadPushed()` 返回**拍平后的数组**，多个文件（`rooms/*.js`）就逐个读、拼起来。
用 `loadTop()` 去读 `push` 写法的文件，会报一个莫名其妙的
`找不到 G.data.x = ...` —— 因为那个文件里压根没有等号。
