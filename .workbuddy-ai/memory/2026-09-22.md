## 一级 / 二级怎么分

- **一级 = 中栏「地图点位状态」** —— 讲"脚下这一格 + 旁边有谁"。

  **不报任务进度**了（进度只在二级区看）。

两块各讲自己那一层，不互相抄 —— 名字和态度不在一级区、二级区各画一遍。

## 踩的坑（都是"改完还看着挺对"的那种）

1. **`replace_all` 改坏复合 CSS 选择器。**
   把 `#tile ` 批量替换成 `#tile, #secondary ` 时，`#tile, #secondary dd.act button,`
   这种**本来就是两条选择器**的地方被拆成了"裸 `#tile`" + "`#secondary dd.act button`"，
   规则落到整个 `dl` 上，而 `#tile` 里的按钮一条样式都没上。
   表现：`✗ 进入按钮是门色的`、`✗ 进入按钮铺满点位状态那一栏的宽` 两条失败。
   → 全部改用 `:is(#tile, #secondary) xxx`（顺带清掉了 `:is(:is(...))` 嵌套）。
   **教训：批量替换字符串会改坏复合选择器结构，改完必须回读确认。**

2. **恒真的空断言。**
   原来写 `T('操作区按内容高度、没被拉满', $('actions').scrollHeight <= $('actions').clientHeight + 1)` ——
   `scrollHeight` **永远 ≥ `clientHeight`**，把代码改坏照样绿（反向验证时它没变红才发现）。
   → 改成量**里面那几组按钮实际占多高**（首尾 `.group` 外框之差）：
   正常 0.4px、改坏 367.4px。

3. **断言里 `(el || {}).className.indexOf('cur')` 会抛 TypeError。**
   元素不存在时 `{}.className` 是 `undefined`，`.indexOf` 直接抛错，
   把后面几十条检查一起带走（反向验证那条只报了"求值抛错"、没报断言）。
   → 加 `clsOf(el) => (el && el.className) || ''`。

4. **1100×700 下"二级操作比操作区高"必挂。**
   操作区那五组按钮本来就要 340px，比剩余空间还多，二级操作只剩 292px。
   → 换成量"**操作区有没有被拉伸**"（更有意义：验的是谁吃剩余空间）。

5. **`#secondary.idle` 跟 `.placeholder` 的 `flex: 1` 冲突。** → 自己写 `display:flex` + 居中。

6. **布局断言要先量真实数字再写。**
   用临时脚本量出 1440×860 / 1100×700 下各面板真实高度（`secondary-panel` 452.5 / 292.5，
   `action-panel` 340.4），量完删掉临时脚本。

## 用户拍板的设计（原话要点）

| 议题 | 决定 |
|---|---|
| 生命 / 灵性的「100」 | 是**上限**，可以被抬高 |
| 生命惩罚档位 | **取最严重的一档**，不叠加 |
| 技能加成 | 加值 + 百分比**两种都支持** |
| 灵性作用 | 「也有惩罚档位，我好像忘记和你说人物还有一个状态栏，会受到一些正面/负面状态，类似被动技能，但是会更频繁的变动」 |
| 上限变化 | 直接恢复 |
| 属性合成顺序 | **加值先加、百分比相加、惩罚最后** |
| 惩罚性质 | 「比如力量10点，血量到60%，他变成了8点，那么回到60%以上，他就回到10点」→ **派生值，不写回** |
| 灵性机制 | 「灵性不影响属性，灵性到20%，会出现一个负面状态，叫灵性枯竭，占时没有效果，后面在加，灵性到0%，负面状态会变为灵性耗尽。」 |
| 神性 | 「参与计算但不显示」→ 后明确**「只用于判定」** |
| 惩罚范围 | 「生命惩罚只影响基础属性和被动技能。」→ **「主动和状态不受削减，加在惩罚之后」** |
| 状态计时 | `step` / `time` / `manual` / `threshold` 三种都支持 |
| 本次范围 | 技能数据结构 + 示例被动 + 示例主动 + 示例状态 |
| 金币 | **删掉** |
| 旧存档 | **不加迁移，直接重开** |
| 技能入口 | 操作区加一组「技能」按钮 |
| 生命显示 | 百分比 + 细进度条 |
| 技能 / 状态显示 | **各占一块** |

## 核心公式（唯一一条属性链路）

```
固有[attr] = (基础 + Σ被动加值) × (1 + Σ被动百分比 ÷ 100)
惩罚系数    = 生命 ≤30% → 0.6 ；≤60% → 0.8 ；否则 1     （按 当前值÷当前上限 判）
最终[attr] = (固有 × 惩罚系数 + Σ状态加值) × (1 + Σ状态百分比 ÷ 100)   再四舍五入
```

三个关键判断：

1. **主动技能统一走"挂状态"生效** → 公式里只有「状态」一项修正，
   不分"技能修正"和"状态修正"两种。`skl_focus` 的 `applies` 指向 `st_focus`。
2. **惩罚是派生值，不写回 `base`** → 生命恢复后属性自动回弹，`base` 永远是 5。
3. **最终属性不存进存档**，每次现算 → 杜绝"改了技能忘了同步属性"的不一致。

灵性**不走属性惩罚**，而是触发状态：≤20% → `st_drained`（灵性枯竭），
0% → 换成 `st_exhausted`（灵性耗尽），两个效果暂空。

## 踩的坑

1. **技能按钮没渲染。** 冒烟抛 `TypeError: Cannot read properties of undefined (reading 'getAttribute')`。
   探针量出 `#actions` 分组是 `移动|行动|存档|其他`（没有「技能」）、`cast 按钮 = 0`。
   根因：`G.ui.renderActions(actionGroups())` **只在 `init()` 里跑一次**，
   那时 `G.state` 还是空的、`G.skills.active()` 返回空数组。
   → `tryCreate()` 和 `boot()` 里各补一句。**任何"拥有的技能变了"的场合都要补这一句。**
2. **1100×700 下一条断言偶发假红（3 遍里红 2 遍）。**
   根因有两层：
   - 台词是**随机挑**的，长短决定折 2 行还是 3 行 → 面板内容高度跟着变；
   - 内容溢出 3.5px 时 `scrollHeight` **取整**成 193、`clientHeight` 190，
     最大 `scrollTop` 只有 3，最后 **0.53px 永远滚不出来** —— 断言容差正好 0.5px。
   修法（两层都要）：**先把前提造出来**（临时 `style.maxHeight='90px'`，量完还回去），
   **再量"露出来多少"**（可见区与按钮的重叠高度 ≥ 按钮高 − 2px），
   而不是量"按钮底边跟容器底边差几像素"。宽窗口下面板 390px 高，不造前提这条是**恒真**的。
3. **反向验证逮出 2 条"抛错中断"**（比"没拦住"更隐蔽 —— 看着像拦住了，其实后面几十条没跑）：
   - 破坏 `attrs` 表时我在 `to` 里写了 `G.rules.DIV_KEY` —— 那正是 `G.rules` 自己的定义体，
     加载时 `G.rules` 还不存在 → 当场抛错。**要用字面量 `'div'`。**
   - 破坏「只给主动技能配按钮」后点了铁骨、`st_focus` 没挂上，
     冒烟里 `G.statuses.find('st_focus').left` 撞 null 抛错 → **是断言不够防御**，
     改成先存变量再判空。同理 `castBtns()[0]` 也要先存再判。
4. **`validate.mjs` 原本没有 skills / statuses 段落** —— 新素材压根没被校验。
   补上时又发现它只认 `G.data.x = [...]` 写法，而技能 / 状态 / 房间都是 `G.data.x.push(...)`
   → 新增 `loadPushed()`，顺手把房间那段重复的解析逻辑收拢过去。
5. **并行 Edit 同一文件又互相覆盖了一次**（`validate.mjs` 里改两个 `loadTop` 调用，

# 第 19 轮（续三）· 按「文档 vs 代码」逐条对账

## 5. 顺带逮到一个**真 bug**：读档 / 导入之后操作区不重画

操作区的技能按钮是按"拥有哪些主动技能"**现生成**的（`main.js` 的 `actionGroups`），
而 `load()` / `onImportFile()` 只调了 `G.ui.refresh()` ——

> 读档和导入是**两处独立的调用点**，各写一条破坏点，只锁一条等于只锁一半。

## 破坏清单 41 → 45 条，并加出**第二种判据**

| 判据 | 写法 | 看什么 |
|---|---|---|
| 改坏代码，等冒烟变红 | 默认 | `✗` 的条数 |
| 塞坏素材，等 validate 报错 | 加 `expect: '那句话'` | 输出里有没有那句话 |

顺带让 `mutate.mjs` 支持 `runner: 'validate'`（默认跑冒烟）。

### ⚠️ 本轮最大的坑：`mutate.mjs` 被超时杀掉，留下改坏的源文件

- 现象：冒烟里 `再用一次是"续期"（refreshed = true）` 一直红，
  同时 mutate 报「`js/skills.js` 里找不到要改坏的片段，清单该更新了」。
- 根因：`node tools/mutate.mjs` 要跑 **3 分钟**，我第一次用前台命令跑，**120s 超时被 SIGTERM**。
  脚本的还原写在 `finally` 里 —— **进程被 kill 时 `finally` 根本不执行**，
  于是 `js/skills.js` 停在 `refreshed: false`（改坏版）上。
- 更阴的是：**它污染了整张清单的结果**。那条断言常年红着，
  于是**每一条破坏点都"拦住了"**，看起来全绿，其实什么都没验到。
- 修：
  1. 把 `js/skills.js` 还原（`refreshed: !added`）
  2. `mutate.mjs` 加 `pending` 跟踪 + `SIGINT / SIGTERM / SIGHUP` 处理器，收到先还原再退出
  3. 跳过的提示里写清"两种可能"（片段失效 / 上次被中途杀掉）
  4. 文件头写明"这个脚本要跑几分钟，别用会超时的前台命令跑"
  5. 文档 `08` 记下这条教训 + 「破坏点变红 ≠ 它锁的规则被拦住了」

### ⚠️ 第二轮：两条破坏点是**假阳性**（改坏了却没有断言变红）

污染清掉之后重跑，暴露出两条：

1. **「单个状态按自己的文字占宽」**：原来改的是 `button` 上的 `width: 100%`。
   但按钮在"宽度由内容决定的 flex item"里，**百分比宽度是空操作** → 不红。
   改成改 `#buffs dd.buff { width: 100%; }`（能拉满的是 `dd` 那一层），
   断言也跟着改成量 **`dd`（标签）** 的宽度。
2. **「背包吃左栏剩余空间」**：把 `1fr` 改成 `auto` 之后，**"背包块变矮了"照样绿** ——
   因为 grid 的 `align-content: stretch` 默认也会把 `auto` 行拉开。
   换判据：**"状态面板里一点多余空白都没有"** ——
   量 `#buffs` 底边 vs 面板内边距以内的底边（用 `getComputedStyle` 取 padding/border，
   CSS 改数值也不会失效）。

教训：**断言量错了层级、或者判据区分不出改坏前后，就等于没写。**
